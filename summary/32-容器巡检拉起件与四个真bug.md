## §32.1 这东西要解决什么

09-27 18:35–19:04 之间，`reseed-cross-seed` 与 `reseed-drive-loop` **先后停了**，
而既有的两道防线**都够不着**这个形状：

| 既有防线 | 它管什么 | 为什么漏了这次 |
|---|---|---|
| `restart: unless-stopped` | 容器**退出** | 只对**退出**生效；**「从没起来过」它不管** |
| `healthcheck` + `autoheal` | `.drive-loop.state` 心跳（**卡死**）| **容器没起来 ⇒ 没有任何进程跑 healthcheck** ⇒ autoheal 无从得知 |

⇒ 一句话：**autoheal 治「卡死」，本脚本治「没起」**。两者**不重叠、不打架**。

★ 动作分档（这是与 autoheal 的边界，别越界）：

- `status ∈ {exited, dead, created, paused}` 或**容器不存在** ⇒ **拉起**（本脚本的活）；
- `running` 但 `health != healthy` ⇒ **只报，不动手**（那是 autoheal 的地盘：
  它会杀容器让 restart 策略接管；**两边同时动手会互相打架** ⇒ 抖动）。

## §32.2 ★★ 最值得记的一条：**夹具太粗 = 整轮验证作废，而且作废得没有声音**

上一段会话（同一个任务的上一轮）**卡在一个"谜题"上**：假 docker 明明没被要求拉起，
可读数恒为「四个都在跑」。当轮花了很久在这上面。

**真因不是脚本，是夹具**：夹具里

    compose) touch "$FLAG"; ...        # 对所有 compose 调用生效

而脚本第 165 行**预检**跑的正是 `docker compose version` ⇒ **预检就把"已拉起"的标志写了**。
⇒ 读数恒绿 ⇒ **后面三个真 bug 全部看不见**。

### 教训

> **判据里的假件必须与被测系统"同分辨率"。**
> 一个把「预检」与「动作」混为一谈的夹具，会让**所有**依赖这个区分的判据一起失效，
> 而且失效方式是**恒绿** —— 没有任何读数会提示你"这轮白验了"。

### 处置

现在那个假 docker **分开记账**：

| 调用 | 记账 | 副作用 |
|---|---|---|
| `compose version` | `PROBE` | **无** |
| `compose ... up -d` | `ACTION` | 翻标志 |

并断言「**预检走的是 `PROBE` 那条**」—— 把这条区分**钉住**，别让人改回一条。

## §32.3 四个真 bug（都是"输出看着正常、含义是反的"）

### ① 双引号串里未转义的反引号 ⇒ **消息被当命令执行**

    say "   ★ 注意：`up -d` 返回 0 **不等于**容器已经健康"

sh 在双引号里把 `` `up -d` `` 当**命令替换** ⇒ 真去执行 `up -d`
（报 `up: command not found`），并把那段话**吞掉**（打出来少一块）。

★★ 讽刺的是：**同一个文件头第 41 行就明文禁了这条** ——

> 「给 shell 看的字符串里只用 ASCII 标点，注释里也**不写反引号**：
>   dash/ash 的取词器会误解成对的全角括号与反引号，把 case/for 结构截断」

⇒ **代码违反了自家的规约**。

★ 判据用**静态**扫（非注释行的双引号串里不许有裸反引号）——
因为它在源码里**看着是完整的**，只有跑起来才咬人。

### ② `bad()` 在「检出」时就置 `RC=1` ⇒ **拉起成功也 exit 1**

文件头第 55 行的契约是 `0 = 四个都在跑（或已成功拉起）`。
而 `bad()` 是 `RC=1`，它在「**发现**容器不在跑」那一步就被调用了。于是：

    容器停 → 检出 → up -d 成功 → 复读通过 ⇒ 这一趟是**成功**的，却 exit 1

**后果有两层，都不轻：**

1. NAS 计划任务每 10 分钟跑一趟 ⇒ **每趟都记失败** ⇒ 真失败时反而看不出（**狼来了**）；
2. 「**已处理好**」与「**拉不起来**」在退出码上**长得一样** ⇒ 运维没法按 rc 分流告警。

**修法**：拆出 `down()`（只打印 ✗、**不置 RC**）给「检出」用；
`bad()` 只留给**真失败**（找不到 compose / `up -d` 失败 / 复读仍不在跑）。

### ③ `for c in $STILL $NEED_UP` ⇒ **给本来好好的容器也发告警**

`NEED_UP` 是「**曾经**不在跑」的集合，**不是**「还没修好」的集合。所以：

- **一个**容器停了 ⇒ **四个**全收信（那三个一直好好的）；
- `drive-loop` 在**两个变量里都出现** ⇒ 循环**跑五遍**（一共四个容器）。

★★ 这是本仓反复钉的「**读数一样、含义相反**」：收到信的运维会以为"这四个都出事了"。
**修法**：只对 `$STILL`（复读后**仍**不在跑的）投。

### ④ 守卫被 UNC 穿透（**在 NAS 侧核实物时才撞出来**）

守卫原来只判两条：`[A-Za-z]:`（盘符）与 `/*`（绝对路径）。
而 **UNC `//NAS/share` 以 `/` 开头** ⇒ **它通过了「绝对路径」那条**。

**实测**（开发机上拿 NAS 的 UNC 路径跑不带 `--selftest` 的版本）：

- `docker inspect` 打到的是**本机 Docker Desktop**（那台机器上真跑着无关容器）
  ⇒ 四个容器全报「不存在」；
- 于是脚本**真的执行了 `docker compose ... up -d`** —— 打到的是**本机的 daemon**
  （Docker Desktop 回 `no such service` 才没造成实际改动）；
- 还试图往 NAS 的 UNC 路径投告警。

⇒ 这就是守卫**存在的理由**，而它**越过了守卫本身**。
**修法**：补 `//*` 与 `*\\*` 两条拒掉。判据**成对**：四种「开发机形状」都 rc=2，
**且真 NAS 路径（`/volume2/...`）必须放行**（只测拦得住 = 把守卫做成永远红）。

## §32.4 ★ 产品决定（用户拍板）：**只在「拉起失败」时告警**

修 ③ 时把告警范围从「所有不在跑的」收窄成「拉起后仍不在跑的」，
于是**成功拉起变成完全静默**。这是一个**产品决定**，我没有擅自定，问过用户。

| 方案 | 取舍 |
|---|---|
| **只在拉起失败时告警**（**选定**）| 不吵；但容器「停过又起来」这件事**事后收不到信**，只能从 rc / 计划任务日志看出 |
| 拉起成功也告警 | 停机**一定**有信；但偶发一次停机也会发一封 |
| 并入每日摘要 | 不单独成信；动静最大 |

★ 代价**认下来**并写进文件头：容器「停过又起来」**事后没有信**。
若要事后有感知，看每日摘要里那段心跳。

★ 连带改了告警**文案**：原来 `title: 容器不在跑：X` 与「只在拉起失败才投」的语义相反
（读信的人会以为「收到信 = 刚才停过」）⇒ 改成 `title: 容器拉不起来：X`，
正文也明说「这封信只在**拉起没成功**时发」。

## §32.5 ★★ 为什么这四个 bug 能同时藏那么久

根因是**一条测试可达性**的问题：

    --selftest  ⇒  强制 DRY=1
    而复读 / 投告警那一段是  [ "$DRY" = 0 ]  才进的

⇒ **脚本最要紧的那条路径（拉起 + 复读 + 投告警）在自带自测下永远走不到。**
⇒ 于是 ②③ 这类「只有走真动作路径才暴露」的 bug **没有任何自测能碰到**。

**处置**：加 `--selftest-live`（假 docker + **允许 `DRY=0`**），
并**注明生产上绝不能用**（它会真去 `up -d`）。门禁用它来覆盖真动作路径。

★ 这条比 bug 本身更值钱：**「有自测」不等于「被测到了」**，
而缺的那一段**恰好是最危险的一段**（会改生产状态的那段）。

## §32.8 ★★ 那条边界：**daemon 身份校验**（2026-09-29 **已修**）

**机器守卫挡不住「长得像 NAS 的绝对路径」。**

实测：在开发机上传 `--compose /volume2/docker_ssd/prowlarr_cross-seed_autohardlink`
**会通过**守卫，然后 `docker inspect` 打到**本机 daemon** ⇒ 四个全报「不存在」
⇒ 读数是「四个都没起」，**真因是「问错了机器」**。

★ 为什么路径守卫挡不了：**那条路径就是生产路径**。

### ✅ 2026-09-29：加了**第二维判据 —— daemon 身份**

用户当场给了 SSH 权限，**实测拿到判据值**（这是原先"只有真机能证"的那个未知）：

| 字段 | 开发机 | **NAS（实测）** |
|---|---|---|
| `docker info --format '{{.Name}}'` | `docker-desktop` | **`iSunker-DS423`** |
| `.OperatingSystem` | `Docker Desktop` | **`Synology NAS`** |

⇒ **两个独立信号都能分辨**，且原假设的 `iSunker-DS423` 是**对的**。

**判据的形状（★ 关键：默认宽松，只拒能确证的）**：

| 读数 | 动作 | 理由 |
|---|---|---|
| **读不出**（命令失败 / 空） | **放行** + 标「身份未验」 | 读不出 **≠** 是开发机；误拒 = 静默挡生产 |
| 命中**已知另一台机器**名单（`docker-desktop` / `Docker Desktop`） | **rc=2 拒绝** | 这是能**确证**的那一半 |
| 其它值 | **放行** + 打印实际值留痕 | 不拿没验过的值当硬判据 |
| 设了 `WATCH_EXPECT_DAEMON=<名>` | 必须**等于**它，否则 rc=2 | 上了 NAS 后可收紧成硬门，**不必改代码** |

★ 这条的性质：**能证伪「这是开发机」，但不断言「这是 NAS」**（后者当年验不了，
现在虽然验了，仍不写死 —— 免得 DSM 改名就静默挡生产）。

★★ **判据成对**（照 §32 ① 的规矩）：
· NAS 身份 + 生产路径 ⇒ **放行**（阳性对照，否则守卫恒红）；
· **开发机身份 + 生产路径** ⇒ **rc=2 且不许有任何 `up -d`**（这是 §32.8 原来的洞）；
· **读不出** ⇒ **放行**（反向对照，不许误挡生产）。
★ 三条都在 `tests/test_watch_containers.py` ① 段**钉住**（45 条里含这三条）。

★ **变异测试**：抠掉开发机拒绝那条分支 ⇒ **恰好**只红
`★★★ §32.8：生产路径 + 开发机 daemon ⇒ rc=2` 这一条 ⇒ 判据**有分辨力**。

★ 实现细节：daemon 探测以 `[ "$DRY" = 0 ]` 为条件 ——
**不能用 `SELFTEST` 门控**：`--selftest-live` 会置 `SELFTEST=1`，
用它当条件会让整段**在测试里永远不可达**（本轮**真踩过**，同 §32.5 的形状）。

★ 顺带实测到的（原先"只有真机能证"的四条）：
① `docker` **不在非 root 的 `PATH` 上**（`/usr/bin:/bin:/usr/sbin:/sbin`），

## §32.14 ★★★ 方案改成**常驻容器**（2026-09-29，用户拍板）—— 已上线并端到端验通

★ §32.12 记的决策是「拉起件留容器外、挂 DSM 计划任务」。**同日用户改主意**：
「**能不能不挂 DSM、全用容器实现**」⇒ 改成 **`reseed-watcher` 常驻容器**。
★ 而**这条在技术上是成立的**（我上一轮说"不能放容器里"**不够准**，在此更正）：

| 说法 | 对错 |
|---|---|
| 「在容器里跑一个能拉起**自己**的东西」不可能 | ✅ 对 |
| 「在容器里跑一个能拉起**别的**容器的东西」不可能 | ❌ **错** —— 那是 `autoheal` 已经在做的事 |

★★ **它唯一盖不住的形状**（"它自己也停了"）由 **`restart: always`** 兜住 ——
而 `always` 正是**业务容器不能用**的那个（会让 `docker stop` 停不住）。
**用在监视器上恰好对：它就该停不住。** ⇒ 两条限制**正好互补**。

### 设计（`docker-compose.yml` 的 `watcher` 服务）

| 项 | 值 | 理由 |
|---|---|---|
| `restart` | **`always`** | 兜 `dockerd` 重启（`unless-stopped` **不会**拉它 —— 那正是本件要补的洞）|
| `profiles` | `["drive-loop"]` | 与 drive-loop/autoheal **同生同死**，不被裸 `up -d` 拉起来 |
| socket | `/var/run/docker.sock:ro` | 与 autoheal **同规格**（只读）|
| image | **`python:3.12-slim`** | ★ 见下"glibc"那条 —— **不是 alpine** |
| 挂载 | 宿主 docker + compose 插件（真身）| 镜像里没有它们 |
| 挂载 | compose 目录**同路径** | ★ 干活的是**宿主 daemon**，compose 文件里是宿主路径 |
| `command` | `sh scripts/diag/watch-containers-loop.sh` | 循环入口 |

### ★★★ 三条**实测**结论（都是踩出来的，别想当然）

1. **必须 glibc 基础镜像（`python:3.12-slim`），不能用 alpine。**
   实测：宿主的 `docker` / `docker-compose` 是 **glibc 动态链接**的，
   在 alpine（musl）里跑报 `docker-compose: no such file or directory`
   —— 那**不是文件不在**（它明明挂着），是**缺 loader**。
   ★ `python:3.12-slim` **已在 NAS 上**（drive-loop 底座）⇒ **不用新拉镜像**。
2. **`/usr/local/bin/docker` 是符号链接**（→ `/var/packages/ContainerManager/target/usr/bin/docker`）
   ⇒ 要挂**真身**。compose 插件同理。
3. **compose 插件的发现路径是 `/usr/local/lib/docker/cli-plugins/docker-compose`**
   —— 实测 `/usr/local/libexec/...`、`/usr/lib/...`、`/usr/libexec/...` **都不认**。

### 循环脚本（`watch-containers-loop.sh`）

★ 三条语义，**每条都对应一个"错了会静默出事"**：
· **单轮 `rc≠0` 绝不终止循环** —— 否则「一个容器拉不起来」会变成
  「**看护容器反复重启**」（`restart: always` 会一直拉它）⇒ 故障被**放大**，

  **这恰好是 §32.12 里"选项 (C)"要补的洞** —— 本文件是它的**最小实现**。

  `watch-containers.sh` 最后一个赢 ⇒ **本脚本的默认值被静默覆盖**）。

  ⇒ **恰好 5 条红**，复原 ⇒ 18/18。

## §32.16 ★★★ 第 7 个真 bug：**观测对账的判据只吃「一种」Found 形状**

**发现于** 2026-09-29 复查上一条告警时（用户问「观测对账是不是读错文件了」）。
★★ **用户的猜测方向是「日志抓错了文件」——方向对，但机制错。文件是对的，是判据只认一半的形状。**

### 症状

`reconcile_watch` 在日报里投出这条（`notify/archive/1790611588662-15-Found.txt`）：

```
title: 观测对账：一条 Found 都没抓到
metrics: fa=0 fb=0
形状行 a == 0，正则行 b == 0
**这不是「干净」** —— 要么真没搜出去过，要么日志抓错了文件。
日志: .../cross-seed/logs/info.current.log
总行数: 27
```

### ⭐ 三条读数摆在桌上，互相矛盾

| 来源 | 读数 |
|---|---|
| `grep -c 'Found'` 那个文件 | **7** |
| `grep -c '] Found '`（判据要的形状） | **7** |
| `S.count_found_lines()` 同一个文件 | **L1 命中 = 2，a = b = 0** |

⇒ 形状**数到了 2 行**（所以 `controls_ok` 为真、判据确实跑到了），
但那 2 行**一行都没进 `a`**，掉进 `other_found`。**文件没错。**

### 根因：cross-seed 有**两种** `Found` 行，判据只描述了一种

那个文件的 `] Found ` 行一共 7 条，是**三种**：

```
2 条  [webhook] Found 1 torrents for {          ← ★ 三行式：本行 +  path: '' + }
2 条  [webhook] Found <片名> [8hex...] on <站> by MATCH from dataDir (...) - exists   ← 单行式
3 条  [inject]  Found 2 torrent file(s) to inject in /config/cross-seeds              ← 已排除，不算
```

而 `orchestrator/state.py` 的 `FOUND_LITS` 六字面量**全部取自单行式**：

```
("L1 `] Found `",        "] Found "),      ← 两种都有
("L2 `[8hex...]`",       None),             ← 只有单行式有
("L3 `] on `",           "] on "),          ← 只有单行式有
("L4 ` by `",            " by "),           ← 只有单行式有
("L5 ` from dataDir (`", " from dataDir ("),← 只有单行式有
("L6 ` - `",             " - "),            ← 只有单行式有
)
```

⇒ L2–L6 **一条都对不上** ⇒ 合取失败 ⇒ 三行式**必然掉进 `other_found`**。
★ 而那 2 条三行式的 L1 命中**确实计入了 `lit_counts`**（L1 就够） ⇒ `controls_ok` 为真
 ⇒ 于是**不报「判据没走到」那条**，而是掉进 `b == 0` 那一支，
 投出上面那条**含义最弱**的告警。**判据把「我识别不了这种行」报成了「本日尚无 Found 行」。**

### ★★ 已复现（把生产那两行逐字抄回来跑）

```
== 三行式（Found N torrents for {） ==
   total_lines=3  a=0  b=0  controls_ok=True
   lit_counts={'L1 `] Found `': 1}
   other_found={'N torrents for': 1}     ← ★ 被静默塞进「别的 Found 行」

== 单行式（by <站>） ==
   total_lines=1  a=1  b=1  controls_ok=True
   lit_counts={L1..L6 全中}
```

### 这不是新出现的形状 —— **它一直都在，而且历史上是主力**

逐日 `grep` 两种形状（NAS 上原始日志）：

| 日期 | 三行式 `Found N torrents for` | 单行式 `by <站>` |
|---|---|---|
| 09-15 | 18 | 35 |
| 09-16 | **536** | **534** |
| 09-17 | **521** | **700** |
| 09-18 | **1154** | 127 |
| 09-19 | 545 | 766 |
| 09-20 | 625 | 875 |
| 09-21 | 467 | 629 |
| 09-27 | 21 | 21 |
| 09-29（当日）| 2 | 2 |

⇒ 三行式在 09-16～09-21 是**每日期几百条的量级** ⇒ **`a` 长期漏计一大块**：
  它数的是「**搜到了什么（单个 searchee + 站）**」，而 `_RE_FOUND` 吃的也是单行式 ——
  于是 `a − b` 的差**恰好是 0**，**判据看起来很健康**，
  而正文却把 `a` 念成「**搜出去的总数**」。★ 这就是 `B.10` 第 14 条那个形状：
  **读数一样、含义相反**。

### ★ 顺带更正 §32 里我给过的一个说法

上一轮我说这条告警「是『抓错文件』的味道（日志文件 27 行，而 docker logs 里满是 Found）」。
**「27 行」那句是错的** —— `info.current.log` 是 **128 行**，27 是 `c.total_lines`，
而 `total_lines` 数的是「**当日日志**」里**同时含 `] Found ` 且落在日期前缀格式里**的行。
⇒ 我把一个**派生计数**读成了**文件行数**，并据此推了个错结论。
（那 2 条三行式是**跨 2 行**的 `{ … }`，真正含判据关键词的确实只有 2 行 ——
所以 27 这个数**本身**也不是错的，是我**念错了它**。）

### 待定：判据的口径该是哪一个（**要先拍板再改**）

1. **`a` 该不该含三行式？** 若含 ⇒ `a` 变成「搜到了多少条」的总量，
   而 `_RE_FOUND` 只吃单行式 ⇒ `delta` 会**常年为正**（几百/天）
   ⇒ `a − b` 这条判据**立刻恒红**。⇒ 要么同时给 `_RE_FOUND` 加三行式，要么**另立一格**。
2. **回灌的状态机要不要改读三行式？** 它现在靠单行式推「哪个站搜到了」（`by <站>`）。
   三行式里**没有站名**（只有 `path:`）⇒ 从三行式里拿不到「哪个站」。
   ★ 但它能拿到**另一维**：这条 `path` 被搜过、且返回了 N 条。
3. **`other_found` 现在把三行式当「别的 Found 行」静默吃掉** —— 这是个**兜底格**，
   任何**没预料到的** Found 形状都会掉进来且**不报警**。
   ⇒ 建议：`other_found` 非空时**报一条告警**（或进 metrics），否则下一个新形状同样静默。
★ 这三条的取舍**不是实现细节，是口径**（本仓老规矩：**口径变了要跟着改名字**）⇒ 先定再改。
