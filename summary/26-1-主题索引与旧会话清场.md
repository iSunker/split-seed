#### 26.5.2 ★★ `notice` 定案：**不搬，保持启用**（2026-09-17 晚）

**用户提问**：「dsm 的 loop 任务停了，但是 notice 还在，这个 notice 能不能也弄到 docker 里面去？
先验证可行性，再决定做不做。」

**① 先确认实体**（没猜）：`notice` 在仓库里 `grep` **0 命中** ⇒ 它是**面板上的显示名**。
用 `sudo /usr/syno/bin/synoschedtask --get` 读出真身：

| ID | Name | State | Command |
|---|---|---|---|
| 9 | `reseed-drive-loop` | **disabled** | `sh …/drive-loop/run.sh` |
| **10** | **`reseed-notify-drain`** | **enabled** | `sh …/notify/notify-spool.sh` |

⇒ **`notice` = ID 10 `reseed-notify-drain`。**

**② 可行性判据（`grep` 说话，不是推断）**：
`grep -n 'notify-spool\|notify/spool\|spool' drive-loop/scripts/drive-loop.py`
⇒ 命中 11 行，**没有一处是"调用 `notify-spool.sh`"**（全是注释 / 打印路径 / `--notify-spool` 参数 / 父目录自检）。
`drive-loop.py:90` 的注释就是答案：**「发信由 NAS 上的 `notify-spool.sh` 完成」**。

**③ 结论：分工，不是重复。**

| 谁 | 干什么 |
|---|---|
| 容器 `drive-loop.py` | **只写** `notify/spool/` 事件文件 |
| DSM `reseed-notify-drain` | **排空**：读 spool → 发信 → 移进 `archive/` |

⇒ **停它 = 告警只进不出，全堆死在 `spool/` 里。搬它 = 也发不出信** ——
`notify-spool.sh` 读的是 **DSM 自己的 `/etc/ssmtp/`**，**容器里没有那个文件**
（容器内跑 `--test-mail` 实测报 `No such file or directory`）。
★ 这一条**反而是"不搬"最硬的证据**：搬进去要**再挂宿主机的 `/etc/ssmtp`**
⇒ 多暴露一份**邮箱口令**给一个容器 ⇒ **净亏**。

**④ 一条被自己的侦察推翻的中间结论（记账）**：我一度判断"两条路在并行排空同一个 spool"，
并**据此推荐"停掉 ID 10"**。`grep` 证明**容器根本不排空** ⇒ **方案 A 的前提被自己否掉**。
★ 这正是"判据必须能红"的用处：假设推翻在**动作之前**。
★ 已进 `ENVIRONMENT.md` `B.10` 第 **17** 条（"我推的当验的"）。
