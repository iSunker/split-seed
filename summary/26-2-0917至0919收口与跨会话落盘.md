#### 补丁（已落盘，`deploy.sh` 268 → 285 行，`bash -n` 通过）

```bash
CR_CHAR=$(printf '\r')            # ★ 不写字面量（见上）；定义在算差异之前
...
    case "$s" in
      *.cmd|*.bat) : ;;           # ★ 例外：那两个**必须**是 CRLF（见 .gitattributes）
      *) LC_ALL=C tr -d "$CR_CHAR" < "$DST/$d.new.$$" > "$DST/$d.new.$$.lf"
         if ! cmp -s "$DST/$d.new.$$" "$DST/$d.new.$$.lf"; then
           mv -f "$DST/$d.new.$$.lf" "$DST/$d.new.$$"
         else rm -f "$DST/$d.new.$$.lf"; fi ;;
    esac
```

* **`.cmd`/`.bat` 排除** —— 那两行为 `drive-loop-once.cmd` 的 `exit=9009` 加的，**别踩第二次**。

#### ★★★ 方法：用 `/proc/<pid>` 的 **PPID 链**判身份（此前只会看 cmdline）

当天排查中出现过一个假警报（见下条），定案的**唯一**手段是读 `/proc` 的**父子链**，
而不是读日志、读 cmdline、或读 `docker ps`。**可复用配方**（`ps`/`pgrep` 在 DSM 与
`python:3.12-slim` **两边都没有** —— BusyBox 精简掉了，`run-resident.sh:211` 那条
`pgrep -f drive-loop.py` 的注释在**本机跑不了**，是个**注释与环境的偏差**）：

```sh
# 列出所有 drive-loop 进程 + 它们的父进程（宿主或容器内都可用；不依赖 ps/pgrep）
for p in /proc/[0-9]*; do c=$(tr '\0' ' ' < $p/cmdline 2>/dev/null); \
  case "$c" in *drive-loop.py*) echo "PID=$p PPID=$(cut -d' ' -f4 $p/stat) CMD=$c";; esac; done
```

```sh
# 定身份三件套：exe（哪个解释器）/ cwd / HOSTNAME（容器 id 还是 NAS 主机名）
ls -l /proc/<pid>/exe /proc/<pid>/cwd
tr '\0' '\n' < /proc/<pid>/environ | grep -iE '^(HOSTNAME|PWD|TZ)='
```

★ **关键分辨力**：
- **PPID 链**能回答「**谁拉起的**」—— 这比 cmdline 本身重要得多（下条假警报就栽在只看 cmdline）。
- `HOSTNAME` 是**容器 id 短串**（如 `c08c341f970e`）⇒ 容器内；`iSunker-DS423` ⇒ 宿主。
- `exe → /usr/local/bin/python3.12` + `cwd → /app` ⇒ **镜像内**（`/app` 是镜像的 `WORKDIR`）。
  ★ 注意与 `run-resident.sh:67` 那句注释**不矛盾**：那里说的 `/usr/bin/python3` 是
  **DSM 自带的路径**，而镜像里 python 在 **`/usr/local/bin/python3.12`**。
- 宿主与容器**共用 pid 命名空间**（容器能看到宿主进程）⇒ 同一个进程**两边 pid 号不同**
  （容器内 `50` = 宿主 `5495`）。★ 拿容器里看到的号去宿主 `/proc` 查会 `No such file`
  —— 这不是"进程没了"，**是号不同**。

#### 二、★ **顺手判明一处"看着像故障"的 `phase` 读数**（**新读数，非故障**）

**现象**：01:40 那三次读到 `phase=running`，而日志显示 09:43 已「等待 45.0 分钟」进睡眠 ⇒ 看着像
「睡眠期相位写错了」= `Heartbeat` docstring 最怕的那个形状（**永远判在跑 ⇒ 静默永久停工**）。

**★ 判明：不是故障 —— 是"收工写入"与"睡眠覆盖"之间的窗口。** 判据（**四次连读**）：

```
01:45:16 / 01:46:19 / 01:47:21 / 01:48:23  四次都是  phase=idle  hb_age≈50s  round=5  正常收工
```

**机理**（读代码定论，非推断）：
`_resident_state(round_no, cur_pack_idx-1, consec, "正常收工")` 写的是 **`"phase": PHASE_RUNNING`**
（`drive-loop.py:2758`）—— 它在 `time.sleep()` **之前**；紧随其后的
`with Heartbeat(phase=PHASE_IDLE): time.sleep(sleep_sec)`（`:3020`）才把相位覆盖成 `idle`。
⇒ **那三次 `running` 落在两者之间**（收工写 → 首拍 IDLE 覆盖，间隔 ≤ 一个 `period=60s`）。
★ **`hb_age` 也印证**：四次都 ≈50s < 60s ⇒ 心跳在正常翻，**不是卡死**。

> ★★ **与 `§29.8` 的关系**：那条的教训是「**`cat` 一次状态文件不是有效的取证动作**」——
> 本条**正是它又一次咬人**：01:40 我只读了"三次/2 分钟"，就差点把它写成故障；
> **再读四次**才看出是窗口。⇒ **判 `phase` 需要跨过一个 `period`（60s）以上的观察窗**，
> 而 01:40 那三次（间隔 65s）**恰好没跨过**那个写→覆盖的窗口。
> ★ 判据（可复用）：**看到 `phase=running` 而 `note` 是「正常收工」时，先别报警 ——
> `note` 与 `phase` 都来自同一个字面量，`note=正常收工` 只说明"上一次落盘是收工那次"，
> 它**不代表此刻不在跑**；要等下一拍 IDLE 覆盖后再读。**

**⇒ 所以现在仍然不是批次间隙**（`phase=idle` 是**睡眠**，而睡眠正是"等待 45 分钟"那段，
下一批会被唤醒）。★ **正确的窗口**：等 `phase=idle` **且**「等待 N 分钟」那行日志的
N 已经耗尽、或直接等下一批跑完的间隙。★ 见下面「怎么判窗口」。
